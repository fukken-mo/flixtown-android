# Cross-device account sync, isolated Preview work

Baseline: 3.8.18 / 10038, a9bd9a7e332393c3e990e104762beb5c7dbb4821.
No production version bump, signing workflow, merge or deployment authorized/performed by this work.

Architecture: Android AccountSync -> HTTPS OnePanel /api/tv-account-sync.php -> three new MySQL tables. Existing Flix adapter validates account/password, then issues a 15-minute sync-purpose session. Account ownership comes solely from that signed session, not client-supplied username. Each exchange revalidates active status. Server stores an opaque username-derived account hash, whitelisted numeric media keys, positions and episode IDs, bounded episode label, watched/list booleans and revisions. No passwords, tokens, stream/image URLs, media, admin notes or third-party keys are stored in sync records.

Scope: movie/series resume, queued next episode and queue-completion marker, Continue Watching membership, watched/unwatched per movie/episode, My List membership per title. Media IDs must remain stable in the same content backend. Settings, device subtitle preferences, reports, notification acknowledgements and credentials are NOT synced. Account renames/ID reassignment require deliberate migration; same username is the existing adapter identity, not an immutable customer UUID.

Local-first: existing Catalog and playback decisions stay local. Threads: the main thread only notes which whitelisted records changed (constant work per save) and commits prepared imports in slices of at most 200 records, one SharedPreferences write per slice. Reading the progress store, building records and every journal write run on one low-priority worker (the journal's only writer, synchronous commits off the main thread, so activity pause/stop never waits for them); HTTP runs on a separate low-priority worker. The one-time migration snapshot lives in its own file, so routine journal writes stay small. While video plays, saves are not captured one by one: they are collected by the once-a-minute heartbeat and when playback stops, and uploads carry at most 40 records. At Home, uploads carry up to 100 records and a full batch triggers up to 8 quick catch-up rounds (an existing history moves at about 800 records per round instead of 40 per minute). Leaving the player collects and uploads its saves and, back at Home, applies changes from other TVs that waited. Background/force-stop has no always-on service or wake lock. On first connection in each process, local records are compared to the journal to recover changes missed before a process exit. Offline journal survives process restart, coalesces each title to its last pending state; next foreground retries with 1-to-15-minute backoff. Network requests have short timeouts, bounded response size and no raw exception logging. While playing, exchanges upload only the small pending changes and never download history. A Home history fetch stops paginating if playback starts; an already in-flight bounded page is deferred. No remote imports while playing or away from Home. Home merges asynchronously and uses existing safe row-refresh behavior rather than restarting activities.

Revisions are microsecond timestamps, at least one above the account's previous revision, so after the database is restored from a backup new revisions are still higher than anything issued before: a revision number is never reused for different data. Restore detection: records are never deleted and a record's revision only grows, so each TV keeps an anchor (the newest record it read, at its cursor revision). If the server no longer has the anchor at that revision, or the cursor is above the account's revision, the TV is told to reset. It then re-reads everything without uploading; where the server's copy is older than the one this TV had seen, or missing, this TV's copy is uploaded again; records newer than what this TV had seen (other TVs, after the restore) are imported normally. A restore therefore never rolls a TV's progress back to the backup.

Conflicts: server-assigned per-account revisions with compare-and-swap on each record; account row lock covers concurrent PHP workers. The first accepted write wins a simultaneous same-record conflict. A stale offline record is replaced by the server record; a newer local edit made while the request was in flight is retained and rebased for the next exchange. This intentionally avoids trusting client wall clocks and maximum-position rules (which would break Start Over). Last received revision is NOT proof the human watched more recently. Independent titles and independent watched/list records merge. Deletions are explicit tombstones so old devices cannot resurrect removed entries. Tombstones are retained. First opt-in imports existing local records with base 0; existing server records win, local-only titles are added. The initial whitelisted local records are retained in a private migration snapshot on this TV until sign-out. Existing legacy saves have no reliable cross-device timestamps, so this cannot infer which old TV was watched last. Signing out discards this device's unsent journal for privacy; already synced data returns on next same-account sign-in. Offline changes not yet synced can therefore be lost on explicit sign-out. A server write already in flight can complete for its original authenticated account but its result cannot be imported into another account.

Account/server/endpoint scope is checked, late callbacks rejected by generation/owner, tokens stay in memory. No transfer from unknown-owner local data. Existing SignOut migration rules still apply. Preview's separate package has separate local data; it does not read production app progress.

Bounds: at most 10,000 records/account (configurable), 100 operations per request, 100 records per page, 100 pages per pass. Each operation is judged on its own: an invalid one, or a new record beyond the account's capacity, is refused with an error in its acknowledgement while the rest of the batch applies; the TV keeps its local data and does not resend that version (a later change is tried again). Records imported from the server are checked on the TV with the server's own rules and dropped if they fail. Limits are per account where possible because many customers can share one public address (carrier NAT, proxies): exchanges 180/15min per account, new sessions 20/15min per account, failed sign-ins 30/15min per address and 100/15min per username, and a 6,000/15min per-address flood ceiling. Small households normally use one exchange/minute/device. Admin lookup load and actual customer capacity must be measured before rollout. No claim of zero playback impact or hardware proof until tests and real-TV checks complete.

Deployment instructions: panel/onepanel-account-sync/INSTALL.md. Additive SQL and two PHP files, two explicit config additions. No cron. Module stays off without config URL; all existing production behavior remains available when backend is absent/down.

Verification: SyncRecord JVM unit tests (including import validation); real MySQL/MariaDB CAS/concurrency/idempotence/pagination/security tests, a 2,000-record history, per-operation refusals and capacity, and database restores (cursor ahead, anchor missing, anchor older, no revision reuse); HTTP endpoint tests with fake adapter, including 40 accounts sharing one address and the failed-sign-in limits; Android instrumentation with independent TV preference stores sharing a fake server. Controlled fixtures only, no customer accounts, Seerr requests or live reports. Device tests cover two-device transfer, removals, server outage, no active-playback imports, edits during an in-flight request, sign-out late callbacks, a 3,000-record history uploaded and imported with the longest main-thread stall measured, no per-save capture during playback, a database restore, switching to a different account on the same TV, and malformed or refused records. They do not measure real streaming playback frame rate or provide real TV hardware proof. Production publishing requires user acceptance and a separate signed release.
